# Specification: catalog-bff-proxy

## Purpose

Define the same-origin Next.js proxy surface for browser-side catalog fetches. When the frontend is served over an HTTPS tunnel (e.g., ngrok), browser catalog requests MUST stay within the visitor's origin so the developer's local Strapi (`localhost:1337`) is reached through the Next.js server, not the visitor's browser. This closes the CORS-over-ngrok regression without backend changes.

## Requirements

### Requirement: Same-origin products proxy

`GET /api/products` MUST exist as a same-origin Next.js route handler. It MUST forward to `${STRAPI_API_URL}/api/products` with the request's Strapi query keys passed through an allowlist. It MUST attach `X-Trace-Id` (reuse incoming or generate UUIDv4), propagate it to Strapi, and echo it in the response. Errors from Strapi MUST be mapped via `mapApiError` into friendly Spanish responses.

#### Scenario: Visitor over ngrok sees real products

- GIVEN a Next.js dev server running locally and reachable via ngrok (HTTPS)
- AND a populated Strapi backend at `http://localhost:1337` returning products
- WHEN a visitor opens `tienda` over the ngrok URL
- THEN the browser issues a same-origin `GET /api/products` (NOT `http://localhost:1337/api/products`)
- AND the products render in the catalog
- AND the browser console shows zero CORS errors and zero mixed-content warnings

### Requirement: Same-origin categories proxy

`GET /api/categories` MUST exist with the same pattern as the products proxy, supporting a simpler allowlist appropriate for category listing (no pagination by default).

#### Scenario: Visitor over ngrok sees real categories

- GIVEN the same ngrok + Strapi setup as the products scenario
- WHEN a visitor opens `tienda`
- THEN the browser issues a same-origin `GET /api/categories`
- AND the categories render in the sidebar/filter
- AND no console errors appear

### Requirement: Friendly error mapping

Upstream errors from Strapi MUST be mapped via `mapApiError` (exported from `src/lib/api.ts`) into Spanish-friendly messages. Raw text from Strapi such as `Internal Server Error` MUST NOT reach the user-facing DOM.

#### Scenario: Upstream 500 surfaces friendly Spanish, no raw 500 in DOM

- GIVEN the proxy route receives a 500 response from Strapi
- WHEN the route catches the error and invokes `mapApiError(500, ...)`
- THEN the response body contains a Spanish-friendly message
- AND the DOM never displays the literal text `Internal Server Error`

### Requirement: X-Trace-Id propagation

Every request through the proxy MUST carry `X-Trace-Id` (UUIDv4). The proxy MUST generate one if the incoming request omits it and MUST preserve an existing one. The proxy MUST forward the trace to Strapi and MUST echo it in the response headers.

#### Scenario: Browser without X-Trace-Id gets one generated by the proxy

- GIVEN a browser request to `api/products` without `X-Trace-Id`
- WHEN the proxy handles the request
- THEN the proxy generates a UUIDv4 trace
- AND the request to Strapi includes `X-Trace-Id: <generated>`
- AND the response headers include `X-Trace-Id: <generated>` (echoed)

#### Scenario: Browser with X-Trace-Id has it preserved end-to-end

- GIVEN a browser request with `X-Trace-Id: abc-123`
- WHEN the proxy handles the request
- THEN the request to Strapi includes `X-Trace-Id: abc-123` (preserved)
- AND the response headers include `X-Trace-Id: abc-123` (preserved)

## Modified Capability: catalog-load-more

### Requirement: Origin-aware fetchApiFull

`src/lib/api.ts` `fetchApiFull` MUST use a base URL that is relative in browser context (`typeof window !== 'undefined'`) and absolute in server context (current env chain). Callers (`getProducts`, `getProductBySlug`, `getCategories`) MUST NOT need code changes.

#### Scenario: Browser context produces relative URL

- GIVEN the helper runs in a jsdom environment (simulating browser)
- WHEN `fetchApiFull('/products', { populate: '*' })` is called
- THEN the resolved URL is `api/products?populate=*` (relative, same-origin)
- AND the call-site code is unchanged

### Requirement: Server callers unchanged

All existing server-side callers (RSC pages, `createPaymentIntentService`) MUST continue using the absolute `STRAPI_API_URL` directly. Existing tests `products-pagination.test.ts`, `api-security.test.ts`, `useProducts.test.ts`, `src/app/__tests__/page.test.tsx`, `src/app/tienda/__tests__/page.test.tsx`, `src/app/tienda/[slug]/__tests__/page.test.tsx` MUST pass untouched.

#### Scenario: Server-side RSC fetch uses absolute URL

- GIVEN a request handled by `src/app/tienda/page.tsx` (server context)
- WHEN the page calls `getCategories()` via `fetchApiFull`
- THEN the resolved URL is `http://localhost:1337/api/categories` (absolute)
- AND the existing `src/app/tienda/__tests__/page.test.tsx` passes unchanged

## Out of Scope

- Backend CORS / Strapi config
- Media `uploads` proxying or next/image changes
- Authenticated-proxy refactors
- Cloudinary migration
- Catalog pagination/sorting/types refactor
- Caching headers (deferred; current `no-store` behavior preserved)
- Ngrok documentation
- Webhooks (already proxied)
